# 예외 인벤토리 대조표 (E1–E8)

기존 예외 목록(`parser/PARSING_NOTES.md`, `parser/README.md`)과 기존 변환기
코드(`parser/*.py`)를 명세의 8개 항목과 대조한 결과다.

각 항목 끝의 **지금** 단락은 그 예외가 현재 파이프라인에서 어떻게 처리되고
어디서 검증되는지를 적는다. "기존에 없음"은 1단계 대조 시점의 사실이고,
지금도 없다는 뜻이 아니다.

분류 기준

| 분류 | 뜻 |
|---|---|
| **기존에 있음** | 기존 코드가 이 상황을 실제로 처리한다. 근거 코드 위치를 적었다. |
| **기존에 있음(암묵적)** | 처리는 되지만 "이 예외를 처리했다"는 의도가 코드에 없다. 다른 규칙의 부수효과다. 규칙이 바뀌면 조용히 깨진다. |
| **기존에 없음** | 처리하지 않는다. |
| **해당 없음** | 그 문서군/경로에 이 상황이 구조적으로 존재하지 않는다. |

가장 중요한 전제 — **기존 변환기는 lxml을 쓰지 않는다.** `html.parser`를 상속한
자체 관대 파서(`_TreeBuilder`)로 트리를 세운다. 그래서 절대 규칙 3(`recover=True`
금지)·4(bytes 금지)는 "기존 코드가 위반하고 있는 것"이 아니라 **XML 파서로
갈아탈 경우 밟게 될 지뢰**다. E1·E2가 "기존에 있음"인 것도 이 설계 덕분이다.

## E1 — bare `&`

**분류: 기존에 있음 (처리 O / 기록 X)**

| 항목 | 내용 |
|---|---|
| 근거 코드 | [major_parser.py:149-155](../parser/major_parser.py#L149-L155) `handle_entityref` (holding:‑, periodic:‑, exchange:213 동일 로직) |
| 기존 목록 | 공통 예외 3 "`&이름` 뒤에 세미콜론을 함부로 붙이면 안 됨" |
| 처리 방식 | `html5` 엔티티 사전에 있는 이름일 때만 실제 문자로 바꾸고, 아니면 `&이름`을 **원문 그대로** 되돌린다. |

기존 목록이 기록한 실측: 무조건 `&이름;`으로 복원했더니 원문 `삼성E&A` →
`삼성E&A;`로 깨진 사례가 exchange에서 **73건**. major 598건 중 `&` 이스케이프
누락이 **103파일**([major_parser.py:47-49](../parser/major_parser.py#L47-L49)).

**남는 구멍**: 몇 건을 어떻게 처리했는지 **아무 데도 기록하지 않는다.** 절대 규칙 2
("처리했더라도 처리했다는 사실이 산출물에 남아야 한다")를 만족하지 않는다.
4단계에서 `record: count`를 붙일 자리다.

이지만, DSD-XML에서는 캡션 말고 본문 꺾쇠가 주다.

**남는 구멍**: E1과 같다 — 처리 건수가 산출물에 남지 않는다.

## E4 — `LIBRARY` 컨테이너

**분류: 기존에 있음(암묵적) — 검증 장치는 없음**

| 항목 | 내용 |
|---|---|
| 근거 코드 | major: [major_parser.py:297](../parser/major_parser.py#L297) `_PASSTHROUGH = {'BODY','LIBRARY','TABLE-GROUP',...}` + [major_parser.py:400](../parser/major_parser.py#L400) 마지막 catch-all.<br>holding·periodic: **catch-all 재귀 한 줄이 전부.** `_PASSTHROUGH` 자체가 없다. |
| 기존 목록 | **없음.** 예상대로 md 파이프라인이 예외를 던지지 않아 목록에 오르지 못했다. |

`grep -c LIBRARY parser/*.py` → major **1**, holding **0**, periodic **0**.
그런데 실측상 holding에 2,025개, periodic에 26,309개의 `LIBRARY` 노드가 있고
전부 정상 통과한다. 즉 **`LIBRARY`라는 문자열을 한 번도 본 적 없는 코드가
28,334개의 LIBRARY 컨테이너를 올바르게 훑고 있다.** major만 이름을 알고 있고,
그마저도 "제목 없이 통과시킬 태그" 목록에 우연히 들어가 있는 것이다.

기존 `_walk`는 태그를 알든 모르든 마지막에 무조건 자식으로 재귀한다. 그래서
`LIBRARY`가 중간에 끼어도 `SECTION-2`에 **도달은 한다.** 명세가 말한 "30% 유실"은
`//SECTION-1/SECTION-2` 같은 **직속 자식 경로**를 쓸 때 생기는 문제이고, 기존
코드는 그런 경로를 쓰지 않는다(절대 규칙 5를 이미 지키고 있다).

다만 두 가지가 걸린다.

1. **의도가 코드에 없다.** major에서 `LIBRARY`가 `_PASSTHROUGH`에 있는 건
   "제목 없이 통과"시키기 위해서지 "컨테이너 유실 방지" 때문이 아니다.
   holding·periodic에는 그 이름조차 없다. 누가 catch-all 재귀를
   "알 수 없는 태그는 건너뛴다"로 바꾸면 조용히 30%가 사라지고,
   **바꾼 사람은 자기가 무엇을 껐는지 알 방법이 없다** — 지운 줄에는
   LIBRARY라는 말이 안 적혀 있기 때문이다.
2. **`//SECTION-2` 개수 = 도달 개수를 확인하는 장치가 없다.** 검증 골든셋 4번
   (`structure`)이 바로 이걸 세우기 위한 것이다.

같은 계열의 실제 사고가 기존 목록에 하나 있다 —
[holding_parser.py:379-390](../parser/holding_parser.py#L379-L390):
`TITLE`이 `SECTION-N` 바로 밑에만 있다고 가정해서 `TABLE-GROUP` 밑 제목을
**136개 중 83개(61%)** 놓쳤던 버그. 원인 구조가 E4와 똑같다(컨테이너가 한 겹 껴서
직속 자식 가정이 깨진다).

**지금 — 두 겹으로 못 박았다.**

1. **전수 대조**: 문서마다 `//SECTION-2` 정규식 개수와 순회 도달 개수를 재서
   `doc.json` 에 남기고(`diagnostics.section2_regex/_reached`),
   `99_validate.py --structure` 가 전건 대조한다. 어긋나면 `severity: error`.
2. **성질검사**: 코퍼스 없이도 즉시 답하는 검사를 붙였다
   ([99_validate.py](../scripts/99_validate.py) `_library_property_test`).
   `LIBRARY` 1겹 / 2겹 / **이름을 모르는 컨테이너** 세 모양을 손으로 만들어
   순회가 통과하는지 본다. 같은 검사가 "직속 자식 순회였다면 몇 개를 잃는가"도
   같이 세어 리포트에 남긴다 — 명세의 30% 유실이 어디서 오는지를 숫자로 남긴다.

의도가 코드에 없다는 문제도 닫았다.
[normalize/tree.py](../src/normalize/tree.py) 에 `CONTAINER_TAGS` 를 두어
`grep -rn LIBRARY src/` 가 **순회 코드에 걸린다.** 조건문으로 쓰지는 않는다 —
`walk()` 는 여전히 태그를 모르든 알든 내려간다. 이름을 적어 둔 유일한 목적은,
순회를 "아는 태그만 내려간다"로 바꾸려는 사람이 그 자리에서 이 문장을 보게
하는 것이다.

## E5 — 표 아닌 TABLE

**분류: 기존에 있음 (md 렌더링 한정) / 구조화 경로에는 없음**

| 항목 | 내용 |
|---|---|
| 근거 코드 | [major_parser.py:464-474](../parser/major_parser.py#L464-L474) `_one_cell()`, 표 4분류 ③ |
| 기존 목록 | major 헤더 주석의 "표 4분류 ③ 1행 1칸 1,538개(27%) → 제목 962 / 번호제목 359 / 각주 124 …" |
| 처리 방식 | 1행 1칸 표는 표로 렌더링하지 않고 제목(`h`) 또는 문단(`p`)으로 강등한다. |

즉 **md에서는** 이미 "이건 표가 아니다"를 판정한다. 그러나 판정 기준이
`rows<=1 or cols<=1`이 아니라 "셀이 정확히 1개"이고, 판정 결과가
`parse_confidence` 같은 형태로 **밖으로 나오지 않는다.** 2단계 `table_router.py`가
받을 자리.

**지금** — [table_router.py](../src/normalize/table_router.py) 의 `classify()` 가
`rows<=1 or cols<=1` 로 판정하고, `scan()` 이 문서 전체를 훑어
`doc['tables']` 에 표 수와 '표 아님' 수를 남긴다. md 렌더링은 이 모듈을 부르지
않으므로 베이스라인은 그대로다 — 판정 결과가 **밖으로 나오게** 만든 것이지
렌더링을 바꾼 것이 아니다.

## E6 — 단위/각주 귀속 방향

**분류: 기존에 없음**

| 항목 | 내용 |
|---|---|
| 근거 코드 | `parser/*.py` 전체에서 `단위`를 의미 있게 다루는 코드 **0곳** (`grep -n 단위 parser/*.py` → 주석 4곳뿐) |
| 기존 목록 | **없음.** 예상대로. |

`(단위 : 억원, %)` 1×1 표는 [major_parser.py:474](../parser/major_parser.py#L474)
의 `return [('p', text)]`로 흘러가 **떠 있는 문단 하나**가 된다. 어느 표의
단위인지는 어디에도 남지 않는다. md를 사람이 읽을 때는 바로 위/아래라 붙지만,
청크로 쪼개는 순간 단위와 숫자가 서로 다른 청크로 갈라진다.

각주(`※`)도 마찬가지다 — [major_parser.py:291](../parser/major_parser.py#L291)에
`_RE_FOOTNOTE`가 정의만 되어 있고 `_one_cell()`은 이걸 쓰지 않는다(제목 정규식
두 개만 검사하고 나머지는 전부 문단). **정의해 놓고 안 쓰는 정규식**이다.

전수 실측 결과 명세의 방향은 맞았다 — 단위 캡션 318,391건 중 **뒤에만** 붙은 것이
54.8%인데 **앞에만** 붙은 것은 0.2%뿐이다. 다만 각주는 조건이 하나 더 붙는다:
각주 캡션 12,055건 중 **45.2%는 양옆 어디에도 진짜 표가 없다.** "각주표는 이전
형제에 귀속"을 무조건 적용하면 없는 귀속을 만들어낸다. 아래 실측표 참조.

**지금 — 붙인다. 붙일 데가 있을 때만.**

| 층 | 무엇을 하는가 | 코드 |
|---|---|---|
| 판정 | 1×1 표가 단위인지 각주인지, 바로 옆 형제가 진짜 표인지 | [table_router.py](../src/normalize/table_router.py) `caption_kind` / `attach_direction` |
| 기록 | 문서마다 `doc['tables']['attach']` 에 `캡션 표 → 붙일 표` 를 남긴다 | [document.py](../src/normalize/document.py) `_table_stage` |
| 사용 | 단위는 조각 문맥 줄에, 각주는 **바로 앞 표 조각 본문에** 붙인다 | [chunk/build.py](../src/chunk/build.py) |
| 검증 | 붙인 수 ≤ 캡션 수, 대상 색인 실재, 방향-색인 정합 + 규칙 성질검사 | `99_validate.py --captions` |

핵심은 **안 붙이는 경우가 규칙의 일부**라는 것이다. 양옆에 진짜 표가 없으면
`attach_direction` 이 `None` 을 돌려주고, 그 캡션은 아무 표에도 귀속되지 않는다.
검증의 성질검사가 이 한 줄을 지킨다 — 각주의 45.2%가 여기 걸린다.

정책의 `table` stage 는 이제 **가동된다**. 정규식 한 방으로 셀 수 없는 판정
(표 모양·형제 위치)이라 정책 엔진이 아니라 코드가 판정하고, 조치 기록만 같은
규칙 id 로 남긴다 — `encoding` stage 와 같은 방식이다.

## E7 — 회계기간 부재

**분류: 기존에 없음**

| 항목 | 내용 |
|---|---|
| 근거 코드 | 기수(`제 N 기`)를 날짜에 매핑하는 코드 **0곳** |
| 기존 목록 | **없음.** |

기존 코드에 날짜를 다루는 곳은 [major_parser.py:736](../parser/major_parser.py#L736)
`AUNITVALUE`를 사람이 읽는 날짜로 바꾸는 함수뿐이다. 이건 **셀 하나의 값**을
포맷하는 것이지, `제 55 기 1분기말`이라는 **헤더 라벨**에 실제 기준일을 물려주는
일이 아니다. 헤더는 `('t', headers, rows)`의 문자열로 그대로 나가고, 그 기수가
어느 날짜인지는 별도 캡션 TABLE에 남아 연결이 끊긴다.

**지금 — 문서 안에서만 잇는다.**

[extract/periods.py](../src/extract/periods.py) 가 문서마다 사전을 만든다.
기수와 날짜가 **같은 줄**에 있는 곳(캡션표가 그렇다)만 사전이 되고, 그 사전으로
문서 전체의 기수 표기를 해석한다. 결과는 `doc['periods']` 에 들어가고,
[chunk/build.py](../src/chunk/build.py) 가 조각 문맥 줄에
`(제 17 기 1분기 = 2023-01-01 ~ 2023-03-31)` 형태로 싣는다 — 조각 하나만 읽어도
**언제의 숫자인지** 알 수 있어야 하기 때문이다.

세 가지를 일부러 하지 않는다.

- **문서 밖에서 날짜를 끌어오지 않는다.** 회사의 결산월을 알면 `제 55 기`를
  추정할 수 있지만 그건 추론이고, 틀린 기간을 자신 있게 말하게 만든다.
- **못 이은 기수는 못 이었다고 남긴다** (`unresolved`). 라벨만 실리고 날짜는
  빈다. 0이나 빈칸으로 채우면 "안 재봤다"와 "없다"가 구분되지 않는다.
- **라벨을 문장으로 늘리지 않는다.** 날짜가 없는 본문 줄에서 `제 N 기` 뒤를
  첫 날짜까지 먹으면 `제 17 기 1분기 3개월 매출액은 …` 처럼 문장이 라벨이 된다.
  그래서 본문에서는 접미사 화이트리스트(분기/반기·말/초·개월/누적)까지만 끊는다.

검증은 `99_validate.py --periods` 다 — 이은 날짜가 **그 문서 산출물 안에 실제로
있는 날짜인가**를 본다. `facts` 와 같은 질문(지어내지 않았는가)이다.

## E8 — ACODE 반복

**분류: 해당 없음(md 경로) / 기존에 없음(구조화 경로)**

| 항목 | 내용 |
|---|---|
| 근거 코드 | [major_parser.py:818-852](../parser/major_parser.py#L818-L852) `to_dict()` |
| 기존 목록 | **없음.** |

명세가 경고한 `{acode: value}` dict 저장은 기존 코드에 **없다.** `to_dict()`는
라벨 경로(`' > '.join(parts)`)를 키로 쓰고, 같은 키가 또 나오면 `#2`, `#3`을 붙여
피한다([major_parser.py:824-828](../parser/major_parser.py#L824-L828)). 그래서
명세가 말한 "1,741→130, 93% 유실"은 이 코드에서는 일어나지 않는다.

대신 **다른 손실**이 있다.

- `to_dict()`는 `--json` 산출물 전용이고 **md 경로는 이 함수를 지나지 않는다.**
  md에서 ACODE는 어디에도 안 남는다(코드는 `('kv', parts, value, code, norm)`
  튜플에 실려 있다가 렌더링에서 버려진다).
- `#n` 접미사는 **문서 안 등장 순서**에 의존한다. 표가 하나 늘거나 순서가 바뀌면
  `항목명#3`이 다른 값을 가리킨다. 위치 기반 키가 아니다.

즉 E8은 "명세가 경고한 그 실수는 안 했지만, 쓸 만한 키도 아직 없다"가 정확한
상태다. 5단계 `extract/acode.py`가 만들 것.

**그리고 명세가 지정한 키도 못 쓴다.** 전수 실측 결과
`(table_idx, row_idx, acode)`는 7,635,332개 중 **27.45%를 잃는다.** 같은 행
안에서 같은 ACODE가 여러 열에 반복되기 때문이고(당기/전기, 지배/비지배 같은
다열 표), 실측 2,095,725건이다. 열 번호를 넣은
`(table_idx, row_idx, col_idx, acode)`는 유실이 **0.00%**다.
→ 5단계는 명세의 3튜플이 아니라 **4튜플**로 간다. "dict 금지"라는 명세의 의도는
그대로 지키되 키를 한 칸 넓힌다. 아래 실측표 참조.

**지금 — 4튜플로 갔고, 문서마다 다시 센다.**

[extract/acode.py](../src/extract/acode.py) 가 `(table_idx, row_idx, col_idx,
acode)` 로 팩트를 뽑아 **리스트**로 쌓는다(dict 로 모으면 키가 겹칠 때 조용히
덮어쓴다). 같은 파일의 `key_stats()` 가 그 문서에서 4튜플·3튜플·`{acode:value}`
각각이 몇 건을 잃는지 **추출한 자리에서 다시 세어** `doc.json` 에 남긴다.

census 로 한 번 재고 끝내지 않은 이유가 있다. census 는 별도 스크립트라
추출기를 고쳐도 다시 울리지 않는다. 문서마다 세어 두면
`99_validate.py --keys` 가 전건에서 `unique_4tuple == facts` 를 확인하고,
키가 겹치는 순간 그 문서가 FAIL 로 뜬다.

**전수 재측정이 뒤집은 것 하나 — 범위를 안 밝히면 오독된다.**

지금 추출된 팩트 **1,609,835개**에서 4튜플 유실은 0.00%인데, **3튜플 유실도
0.00%** 다. 같은 행 ACODE 반복이 **0건**이다. census 가 잰 27.45% 와 정면으로
달라 보이지만 둘 다 맞다 — **재는 범위가 다르다.**

| | 대상 | 팩트 | 같은 행 ACODE 반복 |
|---|---|---:|---:|
| census(1단계) | 네 문서군 전량 TE | 7,635,332 | 2,095,725 (27.45%) |
| acode 추출(지금) | major / holding | 1,609,835 | **0** |
| periodic 표본 재측정 | periodic 12문서 | 70,290 | 30,020 (**42.71%**) |

같은 행에 같은 ACODE 가 되풀이되는 구조는 **정기공시에 몰려 있다.** 그런데
정기공시 주석표 509종은 명세대로 구조화하지 않고 md 청크로 흘려보내므로,
지금 acode 경로에는 그 구간이 통째로 빠져 있다. 그래서 "3튜플로 충분하다"가
아니라 **"3튜플이 깨지는 구간을 아직 안 건드렸다"** 가 정확한 문장이다.

열 번호를 그대로 두는 이유는 그것이다. 추출 범위가 periodic 으로 넓어지는 순간
3튜플은 다시 4분의 1을 잃고, 그때는 이미 쌓인 팩트 테이블의 키를 바꿔야 한다.
지금 넣어 두는 비용은 0 이다. `--keys` 검사도 이 사실을 출력에 같이 적는다 —
숫자만 보고 "열은 필요 없었다"로 읽지 않게.
