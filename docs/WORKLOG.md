## 단계 0 — 파일이 실제로 뭐가 있는지 확인 + 임베딩 건강검진 (2026-08-30)

### 왜 했나
계획서는 특정 파일들이 특정 위치에 있다고 가정하고 쓰여 있었다.
그 가정이 맞는지 먼저 눈으로 확인하지 않으면, 나중에 없는 필드를 참조하는 코드를 잔뜩 짜게 된다.

### 무엇을 알아냈나

**(1) 계획서가 가정한 경로 중 상당수가 실제와 달랐다.**

| 계획서가 있다고 한 것 | 실제 |
|---|---|
| `data/raw/universe.csv` (회사 목록) | 없음. `corpus/universe.csv` 에 있음 |
| `data/raw/manifest.jsonl` (문서 목록) | 없음. `corpus/manifest.jsonl` 에 있음 |
| `data/processed/corpus.db` (재무 수치 DB) | **아예 없음.** 리포 전체에 데이터베이스 파일이 0개 |
| `docs/plan/` 안의 설계문서 6개 | 없음 |
| `CLAUDE.md` (프로젝트 상시 규칙) | 리포 루트에 없었음 (`prompt/Claude.me` 에 내용만 있었음) |

**(2) 가장 중요한 발견 — 청크 파일이 두 벌 있고, 그중 한 벌만 진짜다.**

- `data/processed/chunks.jsonl.gz` : 129만 417조각. 이 리포의 자체 청킹 스크립트가 만든 것.
- `data/processed/chunks_by_10_companies/` 안의 파일 8개 : 합쳐서 61만 4,578조각.

**임베딩(숫자 변환)은 두 번째 것으로만 했다.** 첫 번째 파일은 임베딩 결과와 아무 관계가 없다.
앞으로 만드는 검색기는 전부 두 번째를 봐야 한다. 첫 번째를 잘못 참조하면 조각 번호가 통째로 어긋난다.

**(3) 필드 이름이 계획서와 다르다.** 계획서는 `embed_text`, `corp_name`, `doc_group` 같은 이름을 쓰라고 했는데
실제 파일은 다른 이름을 쓰고 있었다.

| 계획서의 이름 | 실제 이름 | 뜻 |
|---|---|---|
| `embed_text` | `embedding_text` | 임베딩할 때 실제로 넣은 글 |
| `text` | `content` | 사람에게 보여줄 본문 |
| `corp_name` | `company` | 회사 이름 |
| `corp_code` | `stock_code` | 종목코드(6자리) |
| `doc_group` | `disclosure_type` | 공시 종류 |
| `rcept_no` | `receipt_no` | 접수번호 |

**(4) 아주 위험한 함정 하나 — 같은 이름, 다른 값.**

`id_map.parquet`(조각 번호 ↔ 문서 정보 대응표) 에 `corp_code` 라는 칸이 있는데,
여기 들어 있는 값은 **6자리 종목코드**(`097950`) 다.
그런데 `universe.csv` 와 `manifest.jsonl` 의 `corp_code` 는 **8자리 금감원 고유번호**(`00126380`) 다.

이름이 같아서 무심코 섞어 쓰면 회사 필터가 **항상 0건**이 되는데,
에러도 경고도 안 나고 그냥 "검색 결과 없음"으로 조용히 지나간다. 원인 찾기가 매우 어렵다.

**(5) 다행인 것들**

- 조각 수 61만 4,578개가 임베딩 결과·대응표와 **정확히 일치**. 하나도 안 어긋남.
- 회사코드·공시종류가 **비어 있는 조각이 0건**.
- `base_year`(사업연도) 가 정수형(2024)이다. 이게 실수형(2024.0)이었으면 연도 필터가 조용히 전부 실패했을 것이다.
- 조각의 `receipt_no` 가 문서목록의 `rcept_no` 와 **4,204개 전부 연결**된다. 문서 제목·정정 여부를 붙일 수 있다.

### 임베딩 건강검진

계획서가 지목한 검사 스크립트가 리포에 없어서 같은 목적으로 새로 만들었다.

- 만든 파일: **`eval/embed_health_check.py`**
  - 하는 일: 조각 200개를 무작위로 골라 **다시 숫자로 바꾼 뒤**, 원래 저장돼 있던 숫자와
    가장 닮은 조각이 자기 자신인지 확인한다. 자기 자신이 1등으로 안 나오면 어딘가에서
    조각과 숫자의 짝이 어긋났다는 뜻이다.

결과: **200개 전부 자기 자신이 1등.** (정확히 자기 자신 178개 + 글자가 완전히 똑같은 중복 조각이 1등 22개)
자기 자신과의 유사도도 최소 0.9993 으로 사실상 1.0. 이상 없음.

- 보고서: `reports/embed_health.md`

## 단계 0.5 — "지켜야 할 약속" 확정 (2026-08-30)

### 왜 했나
검색기를 만들기 전에 못 박아둬야 할 게 세 가지 있었다.
(1) 조각의 순서를 어떻게 재현하나 (2) "옛날 버전" 표시가 정확한가 (3) 재무제표 조각이 어떻게 생겼나.

### (1) 조각 순서를 재현하는 코드를 만들었다

**문제:** 임베딩 결과는 그냥 숫자 61만 줄이다. 몇 번째 줄이 어느 조각인지는 **순서**로만 안다.
그 순서가 한 칸이라도 밀리면 검색 결과가 전부 엉뚱한 문서를 가리키게 된다.

**만든 파일: `src/search/source.py`**
- `iter_chunks_canonical()` — 원본 조각을 임베딩 때와 **똑같은 순서로** 하나씩 꺼내주는 함수.
- 순서의 근거를 파일이름 정렬이 아니라 `meta.json` 에 기록된 파일 목록으로 잡았다.
  파일이름 정렬은 운영체제나 설정에 따라 달라질 수 있지만, 기록은 안 변한다.

**검증 결과: 61만 4,578줄 전부 일치. 어긋난 줄 0개.** (16초)
글자를 지문처럼 압축한 값(sha1)을 줄마다 대조해서 확인했다.

### (2) "옛날 버전" 표시가 부정확하다는 걸 발견했다 — 이게 이 단계의 핵심

**배경:** 회사가 보고서를 냈다가 틀린 걸 발견하면 `[기재정정]사업보고서` 를 다시 낸다.
그러면 같은 내용의 보고서가 두 벌 있게 되고, 검색할 때 **옛날 버전이 걸리면 틀린 숫자를 답하게 된다.**

기존 코드에 `superseded`(밀려남) 라는 표시가 1만 4,442줄에 붙어 있었다. 이걸 그대로 쓰면 될 줄 알았다.

**확인해보니 이 표시는 전체의 일부만 잡고 있었다.**

기존 표시를 만드는 규칙은 "회사 + 보고서 제목이 같은데 접수번호가 여러 개면, 제일 큰 것 빼고 옛날 것"이었다.
그런데 원본 제목은 `사업보고서 (2024.12)`, 정정본 제목은 `[기재정정]사업보고서 (2024.12)` 로 **제목이 다르다.**
그래서 원본과 정정본이 아예 같은 묶음으로 들어가지 않았다.

결과적으로 이 표시가 잡은 건 **"정정본이 또 정정된"** 경우뿐이었다.

```
정기보고서 중 최신이 아닌 줄 : 12만 3,739줄
  기존 표시가 잡은 것        :  1만 4,442줄
  못 잡고 남은 것            : 10만 9,297줄   ← 옛날 숫자가 그대로 검색됨
```

실제 사례:
```
CJ제일제당 사업보고서(2024.12)
  20250317000648  원본     1,085줄   ← 옛날 것인데 표시 없음
  20250321001604  정정본     867줄
```

**그리고 반대 방향의 함정도 같이 확인했다.**
원래 계획서에는 "정정공시는 기본 제외"라고 적혀 있었는데, 문서목록의 `is_correction`(정정여부) 로
그대로 걸러내면 **정확히 거꾸로 작동한다.** 정정본이 최신이자 옳은 버전이기 때문이다.
정정본을 빼면 틀린 숫자를 답하게 된다.

이 두 가지를 보고하고 멈췄다. (판단은 사람이 하기로 한 사항)

### (3) 재무제표 조각이 어떻게 생겼는지 확인했다

`section_path`(문서 안에서의 위치) 에 재무제표 관련 말이 들어간 조각이 29만 7,836줄 (전체의 48%).
다만 이건 "재무제표 주석", "재무제표 작성기준" 같은 것까지 다 센 수치라 부풀려져 있다.
진짜 표(재무상태표·손익계산서·현금흐름표·자본변동표)만 세면 3만 7천 줄 수준.

**실제 조각 모양 (CJ제일제당 분기보고서 2023.03):**
```
위치: III. 재무에 관한 사항 > 2. 연결재무제표 > (단위 : 천원)
내용: | 구분 | 제 17 기 1분기말 | 제 16 기말 |
      | 유동자산 | 9,917,079,269 | 9,759,274,570 |
      | 현금및현금성자산 | 1,937,702,073 | 1,797,257,804 |
```

여기서 중요한 점 세 가지:
- **단위(천원)는 위치 정보 맨 끝에 있다.** 본문 안에는 없다.
- **기수(제 17 기)는 본문 표의 머리행에 있다.** 표가 여러 조각으로 잘려도 머리행은 조각마다 다시 붙어 있다. 다행.
- **달력 연도(2023년)는 어디에도 안 적혀 있다.** "제 17 기"가 몇 년인지는 문서의 사업연도 정보로 따로 환산해야 한다.

## 단계 0.7 — 옛날 버전을 걸러내는 표 만들기 (2026-08-30)

### 왜 했나
단계 0.5에서 "기존 표시로는 옛날 버전을 다 못 거른다"는 걸 확인했다.
그래서 제대로 된 걸러내기 표를 새로 만들기로 했다.

### 어떤 방식을 골랐나

선택지가 셋 있었는데 (c′) 로 결정됐다.

- (a) 기존 표시 그대로 쓰기 → 10만 9천 줄이 안 걸러짐. 부족.
- (b) 옛날 접수번호는 통째로 빼기 → 확실하지만 **정정본에 안 들어간 내용까지 같이 사라진다.**
- **(c′) 옛날 것을 빼되, 정정본에 같은 위치의 내용이 아예 없으면 그건 남긴다.** ← 이걸로 결정

(b)가 위험한 이유가 실제 데이터로 확인됐다. 정정본은 본문은 다시 내면서
**감사받은 재무제표 첨부·감사보고서를 통째로 빼고 내는 경우가 많다.**

```
CJ제일제당 원본  20250317000648 : (첨부)연결재무제표 144줄, (첨부)재무제표 96줄, 감사보고서 8줄
CJ제일제당 정정본 20250321001604 : 위 항목 전부 0줄 (대신 "정정신고" 52줄이 추가)
```
(b)로 했으면 CJ제일제당의 2024년 감사받은 재무제표가 코퍼스에서 통째로 사라졌을 것이다.

### 만든 것

**`src/search/build_latest_mask.py`** → 결과물 `data/index/latest_mask.npz`

하는 일을 말로 풀면:
1. 정기보고서만 대상으로, `회사 + (제목에서 [기재정정] 떼어낸 것)` 으로 같은 보고서끼리 묶는다.
   - 사업보고서·분기보고서 같은 정기보고서만 묶는다. 계약체결 공시 같은 건 제목이 같아도 매번 다른 사건이라 묶으면 안 된다.
2. 묶음 안에서 접수번호가 제일 큰 것 = 최신본. 나머지 = 옛날 것.
3. 옛날 것의 각 줄에 대해, **문서 안에서의 위치가 최신본에도 있으면 → 제외**,
   최신본에는 아예 없는 위치면 → **남긴다**.
4. `is_latest`(쓸 것인가) 와 `preserved`(옛날 것인데 살려둔 것인가) 두 개의 참·거짓 목록을 파일로 저장.

`data/index/vectors/` 는 손대면 안 되는 폴더라 그 밖(`data/index/`)에 저장했다.

### 결과

| 항목 | 값 | 뜻 |
|---|---|---|
| 정기보고서 묶음 | 897개 (그중 정정된 것 135개) | |
| 옛날 것 총 줄 수 | 12만 3,739줄 | |
| **제외한 줄** | **9만 7,223줄** | 최신본에 같은 자리 내용이 있어서 뺌 |
| **살려둔 줄** | **2만 6,516줄** | 정정본에 없는 첨부·감사보고서 |
| **검색 대상으로 남은 줄** | **51만 7,355줄** / 61만 4,578줄 | |
| 소요 시간 | 19.2초 | |

**살려둔 게 뭔지 확인** (CJ제일제당 원본 1,085줄 중 277줄이 살아남음):
```
127줄  (첨부)연결재무제표 > 주석 > CJ제일제당주식회사와 그 종속기업
 84줄  (첨부)재무제표 > 주석 > CJ제일제당주식회사
  6줄  독립된 감사인의 감사보고서
  4줄  외부감사 실시내용 > 주요 감사실시내용
  ...
```
의도한 대로 **정정본이 빼먹은 첨부 재무제표와 감사보고서만** 살아남았다. 규칙이 제대로 동작한다.

HD현대일렉트릭도 같은 모양 (772줄 중 308줄 보존, 전부 첨부·감사 관련).

### 남는 위험 (사람 판단 필요)

살려둔 첨부 재무제표는 **정정하기 전 숫자**다.
만약 정정이 재무 수치를 고친 것이었다면, 본문(최신)과 첨부(옛날)가 서로 다른 값을 들고
동시에 검색될 수 있다. 정정본에 첨부가 아예 없으니 이 방식으로는 피할 수 없는 한계다.

대응 방법 세 가지 중 하나를 골라야 한다:
1. 그냥 동등하게 취급 (현재)
2. 살려둔 줄은 검색 순위를 뒤로 미루기
3. "이건 정정 전 첨부입니다" 라는 표시를 붙여서 보여주기

## 단계 0.7-보완 — 결정 추록 v2 반영 (2026-08-30)

### 왜 했나
단계 0.7의 규칙이 정본으로 확정됐고, 살려둔 2만 6,516줄(정정 전 첨부 재무제표)의
취급 방법도 정해졌다. 그 방법을 쓰려면 걸러내기 표에 정보가 하나 더 필요해서 추가했다.

### 정해진 취급 방법 — "조건부 버리기"

살려둔 줄을 항상 쓰지도, 항상 뒤로 미루지도 않는다. **문제가 실제로 생길 때만 버린다.**

값이 어긋날 수 있는 상황은 딱 하나다 — **같은 보고서의 최신본과 옛날 첨부가 검색 결과에 같이 뜰 때.**
그래서 이렇게 한다:

> 검색 결과를 조립할 때, 같은 보고서 묶음의 **최신본 조각이 이미 뽑혀 있으면**
> 그 묶음의 살려둔(옛날) 조각은 버린다. 최신본 조각이 하나도 안 뽑혔을 때만 남긴다.

실제로 어떻게 되냐면:

| 질문 | 무슨 일이 일어나나 |
|---|---|
| "CJ제일제당 2024년 매출액" | 본문 III장(최신)이 뽑힘 → 같은 묶음의 옛날 첨부 재무제표는 버려짐. **숫자가 어긋날 일이 없다** |
| "CJ제일제당 감사의견" | 최신본에는 감사보고서가 아예 없음 → 아무것도 안 버려짐. **옛날 감사보고서가 그대로 살아남는다** |

좋은 점은 "옛날 것은 점수를 30% 깎는다" 같은 **사람이 정한 임의의 숫자가 하나도 안 들어간다**는 것이다.
버릴지 말지가 데이터만 보고 결정된다.

### 무엇을 고쳤나

**`src/search/build_latest_mask.py`** 에 세 가지 추가:

1. **`series_code`(보고서 묶음 번호)를 결과 파일에 같이 저장.**
   위의 "같은 묶음의 최신본이 이미 뽑혔나"를 판정하려면 조각마다 어느 묶음 소속인지 알아야 한다.
   숫자 하나로 표현해서 저장했다 (0~1,401번, 총 1,402개 묶음).
   정기보고서가 아닌 조각에도 번호를 준다 — 그쪽엔 살려둔 조각이 없어서 영향이 없고,
   대신 "번호 없음" 같은 예외값을 안 만들어도 돼서 쓰는 쪽 코드가 단순해진다.

2. **자동 회귀 검사 두 줄 추가.** 나중에 규칙을 손댔을 때 조용히 망가지는 걸 막는다.
   - 제외한 줄 수가 옛날 줄 총량(12만 3,739)에 도달하면 → 중단.
     그건 "옛날 것은 무조건 다 버린다"로 퇴화했다는 뜻이다.
   - 검색 대상 줄 수가 (전체 - 제외) 와 다르면 → 중단.
   - (기존에 있던 "살려둔 줄이 0이면 중단"과 합쳐 총 3개)

3. 파일 저장을 압축 방식으로 바꿈.

### 확인한 것

다시 돌린 결과는 이전과 동일하다 (숫자가 안 바뀌어야 정상이다).

```
정기보고서 묶음      897개 (정정된 것 135개)
옛날 줄 총량      12만 3,739줄
제외한 줄          9만 7,223줄
살려둔 줄          2만 6,516줄
검색 대상          51만 7,355줄
보고서 묶음 번호      1,402개
소요                 20.5초
```

새로 넣은 묶음 번호가 제대로 붙었는지 따로 검사했다:
- 번호에 음수(=오류값) 없음
- **살려둔 조각이 속한 81개 묶음 전부에 최신본 조각이 존재함** — 이게 성립해야
  "최신본이 뽑혔으면 버린다" 규칙이 작동한다
- 살려둔 조각은 45개 회사, 전부 정기보고서 소속
- 살려둔 조각은 "검색 대상"으로는 켜져 있음 — 버리는 판단은 검색할 때 하고, 표에서는 안 버린다

### 이번에 바로잡은 위험 하나

원래 설계문서의 코드는 조각의 위치를 비교할 때 **문서 제목까지 포함해서** 비교하게 돼 있었다.
그런데 제목이 `사업보고서 (2024.12)` 와 `[기재정정]사업보고서 (2024.12)` 로 서로 다르기 때문에
**모든 옛날 조각이 "최신본에 없는 내용"으로 판정돼 하나도 안 걸러졌을 것이다.**

더 나쁜 건, "살려둔 줄이 0이면 중단" 검사는 이 경우 통과해버린다는 점이다
(0이 아니라 12만 3,739 전부가 살아남으므로). 그래서 오류가 안 잡힌 채로 지나갔을 것이다.

단계 0.7에서 문서 제목을 떼고 비교하도록 만든 게 결과적으로 필수 수정이었다.

### 아직 안 한 것 (다음 단계에서 할 일로 기록)

"조건부 버리기"는 표만으로는 완성되지 않는다. 검색기(1-C)를 만들 때 아래를 넣어야 한다.

- **버리는 순서가 중요하다.** 문서당 개수 제한과 중복 제거를 **다 끝낸 뒤**,
  최종 개수(top_k)로 자르기 **직전**에 버려야 한다.
  먼저 잘라버리면 버린 자리가 안 채워져서 결과 개수가 모자라게 된다.
- 살려둔 조각이 최종 결과에 남으면 출처에 표시를 붙인다:
  `※ 자동 주석(공시 원문이 아님): 정정 전 첨부본(접수 2025-03-17). 이후 정정본이 존재하나 이 섹션은 정정본에 없음`
- 시스템 프롬프트에 한 줄 추가: 정정 전 자료의 숫자를 인용할 땐 정정 전임을 답변에 밝힐 것.

## 단계 1-A — 회사 이름 알아듣기 + 문장 쪼개기 (2026-08-30)

### 왜 했나
검색을 하려면 두 가지가 먼저 있어야 한다.
1. 사람이 "현대차" 라고 쳐도 **어느 회사인지 알아내는 것**
2. 문장을 **검색용 낱말로 쪼개는 것** (BM25 방식이 낱말 단위로 세기 때문에)

### 먼저 한 것 — kiwipiepy 설치

한국어 낱말 쪼개기 도구다. 계획서에 사람이 설치하기로 돼 있었는데 안 돼 있어서 제가 설치했다.
(`kiwipiepy 0.23.2`)

### (1) 회사 이름 알아듣기 — `src/search/aliases.py`

**별칭 사전을 데이터에서 긁어모았다: `config/aliases.yaml`**

조각마다 `aliases` 라는 칸에 그 회사의 다른 이름들이 이미 들어 있었다.
61만 조각을 전부 훑어 회사별로 모으고, `universe.csv` 의 정식명·상장명·영문명과 합쳤다.
**없는 별칭을 지어내지 않았다.** 데이터에 있는 것만 담았다. 70개사 · 별칭 429개.

예시:
```
SK하이닉스 : (주)SK하이닉스 / SK하이닉스 / SK하이닉스주식회사 / sk하이닉스 /
             에스케이하이닉스(주) / 에스케이하이닉스주식회사
JYP Ent   : (주)JYP Ent / (주)제이와이피엔터테인먼트 / JYP Ent / JYP Ent. /
             JYP Ent주식회사 / 제이와이피엔터테인먼트 / 주식회사제이와이피엔터테인먼트
```

**이름을 비교하기 전에 표준형으로 바꾼다.**
`(주)`, `주식회사`, `㈜` 같은 법인격 표기와 띄어쓰기·괄호·마침표를 지우고 소문자로 만든다.
그래서 `(주)삼성전자` `삼성전자주식회사` `삼성 전자` 가 전부 같은 것으로 취급된다.

여기서 함정이 하나 있었다. 영문 이름의 `Inc.` 를 안 지우면
`Alteogen Inc.` 안에 **`nc` 라는 글자가 들어 있어서** 회사명이 진짜 `NC` 인 엔씨소프트를
찾을 때 알테오젠까지 후보로 딸려 나온다. 그래서 영문 법인격(`Inc`, `Ltd`, `Corp` 등)은
**낱말 단위로** 떼어냈다. 통째로 문자열 치환하면 회사 이름 자체가 깎이기 때문이다.

**찾는 순서는 세 단계다.**
1. **완전히 같은 이름**이 있으면 그것만 본다 (`KT` → 케이티)
2. 없으면 **질의가 별칭 안에 들어 있는 것**을 찾는다 (`하이닉스` ⊂ `SK하이닉스`)
3. 그래도 없으면 **별칭이 질의 안에 들어 있는 것**을 찾는다 (`삼성전자 반도체` → 삼성전자)

각 단계에서 후보가 **딱 하나면 확정, 둘 이상이면 "모르겠다"** 로 답한다.
**절대 찍어서 하나를 고르지 않는다.** `SK` 처럼 애매하면 후보 목록을 그대로 돌려준다.

**돌려주는 것:** 8자리 금감원 번호(`corp_code`)와 6자리 종목코드(`stock_code`) **둘 다**.
단계 0에서 발견한 "같은 이름 다른 값" 함정 때문이다. 검색 필터에는 6자리만 쓴다.

### (2) 문장 쪼개기 — `src/search/tokenize_ko.py`

`LIG넥스원의 2024년 유형자산 취득액은 3,908,761백만원이다`
→ `['lig넥스원', '2024', '년', '유형', '자산', '취득', '액', '3,908,761', '백만', '원', '3908761']`

신경 쓴 것 네 가지:

1. **회사 이름이 쪼개지면 안 된다.** 그냥 두면 `LIG넥스원` 이 `LIG` + `넥스` + `원` 으로
   갈라진다. 그래서 별칭 547개를 전부 "이건 고유명사다" 라고 도구에 미리 등록했다.
   등록 거부 0건.
   - **이 등록은 색인을 만들기 전에 끝나 있어야 한다.** 색인을 만든 뒤에 단어를 추가하면
     이미 만든 색인에는 반영이 안 돼서 61만 건을 전부 다시 만들어야 한다.
     그래서 사전을 확정한 다음에 1-B로 넘어간다.
2. **금액 숫자를 살린다.** 쪼개기 도구는 `3,908,761` 을 조각낸다.
   공시 질문은 금액 자체가 검색어인 경우가 많아서, 원문에서 숫자를 따로 긁어
   **콤마 있는 형태와 없는 형태를 둘 다** 넣었다.
   - 다만 도구가 이미 같은 글자를 내놨으면 다시 넣지 않는다.
     그냥 붙이면 같은 숫자가 두 번 센 걸로 돼서 점수가 부풀려진다.
3. **불규칙 활용을 놓치지 않는다.** 쪼개기 도구는 불규칙 동사에 `VV-I`, `VV-R` 처럼
   꼬리표를 붙인다. `VV` 만 찾으면 이것들이 빠지므로 `-` 앞부분만 떼어 비교했다.
4. **한 건씩 부르지 않는다.** 1,000개를 통째로 넘겨야 여러 CPU가 나눠 일한다.
   for 반복문 안에서 하나씩 부르면 코어를 8개 줘도 1개만 쓴다.

```
네이버     14,950      삼성전자  13,927      삼성화재     13,871
```

`전자` 같은 일반명사가 수십만 회로 튀는 상황은 **없었다.**

### 그런데 다른 문제를 찾았다

빈도만으로는 안 보여서, 각 별칭이 **다른 낱말 속에 박혀서 걸리는 비율**을 따로 쟀다.
(한국어는 조사가 뒤에 붙으므로 "앞 글자가 한글이면 다른 낱말의 일부"로 보는 방식)

그리고 실제로 쪼개기 도구를 **사전 켠 상태 / 끈 상태**로 돌려 비교했다.
이게 결정적이었다.

**괜찮았던 것 — 걱정이 기우였던 부분**

`NC` 는 46,161회 중 90%가 `INC.`, `USANCE`, `FINANCIAL`, `AGENCY` 같은 **영어 단어 속**이었다.
그래서 위험해 보였는데, 실제로 돌려보니 쪼개기 도구는 영어 단어를 통째로 유지한다.
```
'XL8 INC. 및 공동기업'      사전 ON  -> ['xl','8','inc.','공동','기업']
                            사전 OFF -> ['xl','8','inc.','공동','기업']   (같음)
'LPL FINANCIAL WORLD'      ON/OFF 모두 -> ['lpl','financial','world']
'KB-KTB혁신기술...'        ON/OFF 모두 -> ['kb','ktb','혁신',...]
```
영문 별칭(`NC`, `KT`, `OCI`, `HMM`)은 등록해도 영어 단어를 부수지 않는다. **문제 없음.**

**진짜 문제 두 가지**

1. **`에스엠` 이 무관한 회사 이름을 부순다.**
```
'와이에스엠씨제일차 전자단기사채'
   사전 ON  -> ['와이','에스엠','씨','일','차','전자','단기','사채']   ← 부서짐
   사전 OFF -> ['와이에스엠씨제일차','전자','단기','사채']              ← 정상
```
`와이에스엠씨제일차`(YSMC)는 에스엠엔터테인먼트와 아무 상관이 없는 유동화회사다.
`엘에스엠트론`, `엘에스엠앤엠` 도 같은 식으로 부서진다. 이런 경우가 1만 2,517회 중 1,480회.

2. **`(주)` 가 붙은 표기를 등록하니 덩어리가 너무 커졌다.**
```
'에이치디현대중공업(주) 대표이사'
   사전 ON  -> ['에이치디현대중공업(주)','대표','이사']   ← 통짜 한 덩어리
   사전 OFF -> ['에이치디','현대중공업','주','대표','이사']
```
ON 쪽은 `현대중공업` 으로 검색해도 이 덩어리와 안 맞는다. **검색이 오히려 안 된다.**
이런 `(주)`·`㈜`·`주식회사` 포함 표기가 429개 중 **258개**다.

**그리고 짧은 한글 이름은 애초에 등록할 필요가 없었다.**
사전을 끄고 8개를 시험해보니 전부 이미 한 덩어리로 나온다.
```
기아 / 네이버 / 에스엠 / 이마트 / 카카오 / 케이티 / 하이브 / 현대차  → 8개 모두 정상
```
반대로 사전이 **꼭 필요한** 것은 도구가 쪼개버리는 이름들이다.
```
LIG넥스원 -> ['lig','넥스원']      한전기술 -> ['한전','기술']
시프트업  -> ['시프트','업']        파마리서치 -> ['파마','리서치']
세아베스틸지주 -> ['세아베스틸','지주']
```

### 제안 (사람 판단 대기 중이라 아직 안 고침)

- `config/aliases.yaml` 의 429개는 **그대로 둔다.** 회사 이름 찾기(`resolve_company`)는
  완전 일치로 비교하므로 별칭이 많을수록 좋고, 위 문제와 무관하다.
- **낱말 쪼개기 사전에 넣는 것만 걸러낸다.** 258개(법인격 표기 포함) + 8개(한글 3자 이하)를 빼면
  **163개**가 남는다. 이렇게 해도 **70개 회사 전부 최소 한 개 표기는 사전에 남는다.**

즉 파일 하나(429개)를 두 군데가 서로 다른 방식으로 쓰게 하는 것이다.

### (2) BM25 색인기를 만들었다

**BM25가 뭔가** — 임베딩(뜻이 비슷한 걸 찾는 방식)과 달리, **단어가 실제로 몇 번 나왔는지**로
점수를 매기는 방식이다. 흔한 단어는 점수를 깎고, 긴 문서는 불리하게 보정한다.
숫자·고유명사처럼 "그 글자 그대로" 찾아야 하는 질문에 강하다.

**외부 라이브러리를 쓰지 않고 직접 만든 이유:**
우리 검색기는 회사·연도로 **먼저 좁힌 뒤** 그 안에서만 점수를 낸다.
시중 라이브러리는 "전체에서 상위 몇 개"를 뽑는 걸 전제하므로,
회사 하나로 좁히면 결과가 0건이 된다.

**미리 계산해두는 구조.** 문서 쪽 가중치를 색인 만들 때 다 곱해둔다.
검색할 때는 질의어에 해당하는 **열만 꺼내서 더하면** 끝이라 빠르다.

**메모리 낭비를 피한 부분:**
- 값을 파이썬 리스트로 쌓으면 9천만 개에서 수 GB를 버린다 → `array.array` 사용
- 열을 꺼낼 때 `getcol()` 을 쓰면 호출마다 행렬 객체를 새로 만든다 → 내부 배열을 직접 잘라 씀

**색인 대상 글자:** 회사명 + 문서제목 + 문서 안 위치 + 본문.
본문은 임베딩용 텍스트가 아니라 `content` 를 쓴다.

만든 파일:

| 파일 | 하는 일 |
|---|---|
| `src/search/bm25_build.py` | 색인 만들기. `--limit` 로 일부만 시험 가능 |
| `src/search/bm25.py` | 검색. `score()` 는 **원점수 그대로** 돌려준다 |

`score()` 를 정규화하지 않은 이유 — 나중에 "답이 없는 질문"을 걸러낼 때
점수의 절대값이 필요하기 때문이다. 0점은 "질의어가 하나도 안 나옴"을 뜻한다.

### (3) 색인 만들기 전 행 순서 재검증

색인의 몇 번째 줄이 어느 조각인지는 순서로만 안다. 그래서 매번 다시 확인한다.

### 실패한 5b — 규칙 자체의 문제였다

"CJ제일제당 감사의견" 을 물으면 정정 전 원본에만 있는 감사보고서가 나와야 하는데 안 나왔다.
원인을 파보니 **검색은 완벽했다.** 순위를 매긴 직후 상태를 보면:

```
 1위  독립된 감사인의 감사보고서            ← 원본에만 있음 (정답)
 2위  내부회계관리제도 감사 또는 검토의견     ← 원본에만 있음 (정답)
 3~4위 목 차                            ← 원본에만 있음
 5위  분기보고서 > V. 회계감사인의 감사의견 등
 ...
 8위  [기재정정]사업보고서 > V. 회계감사인의 감사의견 등   ← 최신본
```

정답이 1·2위에 정확히 올라왔다. 그런데 규칙이 이렇게 돼 있다:

> 같은 보고서 묶음의 최신본이 후보에 이미 있으면, 그 묶음의 정정 전 자료는 버린다

8위에 최신본이 하나 있다는 이유로 **1·2위가 버려졌다.**
그런데 8위는 "V. 회계감사인의 감사의견 등"(본문 요약)이고 1위는 "독립된 감사인의 감사보고서"(첨부 원문)다.
**서로 다른 자리라 값이 충돌할 수가 없다.** 보완 관계지 대체 관계가 아니다.

반대쪽도 확인했다. "매출액" 질의에서는 이렇게 나온다:
```
 1~2위  [기재정정]사업보고서 > 영업부문 정보     ← 최신본
 9~10위 원본 > (첨부)연결재무제표 > 총매출액      ← 정정 전
```
여기서는 최신본이 위에 있고 정정 전 자료가 아래에 있다. 값 충돌이 실제로 가능한 경우다.

**즉 두 경우를 가르는 건 "묶음이 같은가"가 아니라 "누가 더 위에 있는가"였다.**

### 제안 (아직 안 고침 — 승인 대기)

규칙을 한 줄만 바꾸면 두 경우가 다 맞는다.

> 정정 전 자료를 버리는 조건: 같은 묶음의 최신본이 **그보다 위 순위에** 있을 때만

- "매출액" → 최신본이 1~2위, 정정 전이 9~10위 → **버림** (의도대로)
- "감사의견" → 정정 전이 1~2위, 최신본이 8위 → **안 버림** (의도대로)

임의로 정한 숫자가 안 들어가고, 원래 결정문의 두 예시가 그대로 재현된다.

다른 선택지도 있다:
- 아예 안 버리고 "정정 전 첨부본" 표시만 붙인다 (표시 기능은 이미 구현돼 있음)
- 현행 유지 — 다만 이 경우 감사보고서·첨부 재무제표 2만 6천 행이 사실상 검색되지 않는다

| 질문 유형 | BM25만 | + 임베딩(현재) |
|---|---|---|
| 단순 조회 | 87% | **95%** |
| 여러 곳 종합 | 74% | **81%** |
| 복합 추론 | 94% | 94% |

앞서 BM25가 못 찾던 **구어체 질문이 실제로 개선**됐다.

글자가 안 겹쳐도 뜻으로 찾아내기 시작했다.

## 참고 — Question 폴더 (평가용 질문, 2026-08-30 확인)

`Question/질문_(수정해서 다시 할 것)/` 에 사람이 만든 평가 질문이 있다. 나중에 쓴다.

| 종류 | 개수 | 정답 |
|---|---|---|
| `benchmark_<회사>_<연도>AR.json` 42개 | 시나리오 252건 (회사 40종) | **있음** |
| `benchmark_master_templates_24.json` | 템플릿 24종 | 채점 기준만 |
| `bench_q_part01~03_*.json` | 질문 318건 (회사 15종) | 없음 |

시나리오는 6종 균등: `search_closed`(단일 수치) / `search_open`(서술) /
`multi_closed` / `multi_open` / `complex_closed` / `complex_open`.

`doc_info` 에 접수번호가 적혀 있어 정답 문서를 특정할 수 있다. 예를 들어
CJ제일제당 2024년 문항은 `20250317000648`(원본)과 `20250321001604`(정정본)를 함께 지목하는데,
이건 단계 0.7에서 다룬 바로 그 정정 사례다.

폴더 이름이 "수정해서 다시 할 것" 이므로 확정본으로 보지 않는다. 단계 2에서 확인 후 사용.
