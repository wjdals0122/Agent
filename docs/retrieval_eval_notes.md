# 질의 실험 환경

임베딩된 61만 청크에 실제 질문을 넣어 **맞는 근거를 물어오는지** 확인하는 환경이다.
답변 생성(LLM)은 아직 붙이지 않았다 — 근거가 틀리면 생성기를 바꿔도 소용없으므로 검색부터 본다.

## 준비 (1회)

```bash
python -m src.eval.chunk_store --build   # row -> 원본 JSONL 바이트 오프셋 (약 18초)
```

벡터 인덱스에는 표시용 원문(`content`)이 없다. 3GB를 통째로 메모리에 올리지 않으려고
줄마다 오프셋만 적어두고 상위 k건만 seek 해서 읽는다. 빌드할 때 `chunk_id` 순서를
`id_map.parquet`과 전량 대조하므로, row 순서 계약이 깨졌다면 여기서 잡힌다.

## 쓰는 법

```bash
python -m src.eval.ask "삼성전자의 주주환원 정책은?"              # 단건
python -m src.eval.ask "유상증자 목적" --company 카카오 --year 2024 -k 5
python -m src.eval.ask "삼성전자와 SK하이닉스의 매출액 비교" --latest-only   # 회사 2곳이면 자동 분할
python -m src.eval.ask                                            # 대화형 (권장)
python -m src.eval.run_eval -k 5                                  # 질문 세트 일괄 -> 근거 리포트
python -m src.eval.sweep                                          # 설정 그리드 비교
python -m src.eval.gpu_guard --watch                              # 온도 감시
```

모델 로드에 20~65초가 걸린다. 여러 질문을 볼 거면 인덱스를 한 번만 올리는 **대화형**을 쓸 것.

대화형 지시어: `/company 삼성전자` `/year 2023` `/group periodic` `/k 8` `/w 1.0` `/full` `/reset` `/gpu` `/q`

## 점수와 채점

`score = w_dense × (dense 코사인) + w_sparse × (sparse lexical 내적)` — **기본 1.0 / 1.0**.

청크 단위 정답 라벨이 없으므로 [questions.jsonl](../src/eval/questions.jsonl)에 약한 기대치를 적어두고
[metrics.py](../src/eval/metrics.py)로 채점한다.

- `company` — 기대 회사. 상위 결과가 그 회사에서 나왔는가 (개체를 제대로 잡는가)
- `expect_any` — 기대 섹션 키워드. 상위 결과의 섹션 경로·문서 제목에 하나라도 걸리는가

`expect_any`는 표현이 조금만 달라도 놓친다. 절대값보다 **설정을 바꿨을 때의 상대 변화**를 보는 데 쓴다.
`strict@1`(1위가 회사·섹션 모두 적중)이 실제로 답을 만들 수 있는 상태에 가장 가깝다.

```
├── retrieval_eval.json    # 같은 내용의 기계 판독본 (생성 단계 입력으로 그대로 쓸 수 있다)

```

## 실측 결과 (2026-08-26, 40문항 top-5)

### 1. sparse 가중치는 1:1이 맞다 — 0.3은 낮았다

같은 40문항을 가중치만 바꿔가며 재랭킹했다 (질의 인코딩은 문항당 1회, 전체 61초).

| w_dense | w_sparse | section@1 | section MRR | company@1 | strict@1 |
| --- | --- | --- | --- | --- | --- |
| 1.0 | 0.0 (dense만) | 0.750 | 0.801 | 1.000 | 0.719 |
| 1.0 | 0.3 (첫 기본값) | 0.825 | 0.838 | 1.000 | 0.812 |
| **1.0** | **1.0** | **0.900** | **0.913** | **1.000** | **0.906** |
| 1.0 | 2.0 | 0.900 | 0.908 | 1.000 | 0.906 |
| 1.0 | 3.0 | 0.875 | 0.900 | 1.000 | 0.875 |
| 1.0 | 10.0 | 0.800 | 0.863 | 0.969 | 0.750 |
| 0.0 (sparse만) | 1.0 | 0.775 | 0.838 | 0.969 | 0.719 |

- **1:1이 최적**이고 2.0까지 평평하다가 그 뒤로 내려간다. 처음 넣었던 0.3에서 1.0으로 옮긴 것만으로
  section@1이 **0.825 → 0.900**, strict@1이 **0.812 → 0.906** 올랐다.
- dense만 쓰면 회사는 100% 맞히지만 섹션을 자주 놓친다. sparse만 쓰면 회사 적중이 깨진다(0.969).
  **개체는 dense가, 섹션 안 용어는 sparse가 잡는다.** 둘 다 있어야 한다.

현재 기본 설정에서:

- 회사 적중 @1 **100%** / @5 **100%** (32문항)
- 섹션 적중 @1 **90%** / @5 **95%** · MRR **0.913** (40문항)
- 1위가 회사·섹션 모두 적중 **91%**

### 2. 회사 하드필터는 순위를 바꾸지 않는다

`--filter-mode both`로 같은 질문을 필터 없이 한 번, 회사 필터를 걸고 한 번 돌렸다.
**모든 지표가 소수점까지 같았다.** 질문에 회사명이 들어 있으면 임베딩이 61만 건 중에서
알아서 그 회사로 간다. 같은 그룹 회사를 섞어 일부러 헷갈리게 해도 마찬가지였다.

> 삼성전자/삼성전기/삼성중공업/삼성화재해상보험, 한미반도체/한미약품,
> 우리금융지주/우리기술, 한화오션/한화에어로스페이스, HD현대중공업/현대건설 — 전부 @1 적중.

필터는 정확도용이 아니라 **후보를 줄여 오답 가능성을 없애는 안전장치**로 본다.
회사명이 질문에 없는 이벤트성 질의(예: "유상증자를 결정한 이유는?")에는 여전히 필요하다.

### 3. 표 청크가 숫자 질문에 제대로 올라온다

SK하이닉스 매출액 질문의 1위가 「IV. 이사의 경영진단 > 3. 재무상태 및 영업실적」의
요약 손익계산서 표였다. 이마트 점포 수 질문의 1위는 「XII. 상세표 > 4. 국내설비 현황(상세)」로
양재점·통영점 등 점포 목록이 그대로 들어 있다. 청킹 때 표 헤더를 분할 조각마다 반복한 것이
여기서 값을 한다.

### 4. 비교 질의는 단일 검색으로 안 된다 — 한쪽 개체가 통째로 사라진다

"삼성전자와 SK하이닉스의 최근 매출액을 비교해줘"를 그냥 넣으면 **상위 20건이 전부 SK하이닉스**다.
삼성전자는 한 건도 없다. LG에너지솔루션 vs 삼성SDI도 상위 20건이 전부 삼성SDI다.
질의 벡터가 두 개체의 혼합이라 승자독식이 일어난다.

이게 이 실험에서 나온 가장 위험한 실패다. 상위 k를 그대로 생성기에 넘기면 **한쪽 숫자만 보고
비교를 지어낸다.** 근거가 다 그럴듯해서 틀렸다는 티도 안 난다.

`search_multi()`가 세 가지를 한다.

1. **개체 인식** — 인덱스에 든 회사는 70개짜리 닫힌 집합이라 질의문 부분 문자열 매칭으로 잡는다.
   긴 이름부터 훑어 겹치는 구간을 걸러낸다.
2. **부분질의 재작성** — 회사마다 다른 회사 이름(과 붙은 조사)을 지운 질의를 새로 인코딩한다.
   `"삼성전자, SK하이닉스, 삼성SDI의 배당 정책을 비교해줘"` → `"삼성전자 배당 정책을 비교해줘"`
3. **회사별 하드필터 + k 분배 + 번갈아 싣기** — 상위가 한 회사로 채워지지 않게 한다.

비교 8문항 실측:

| | 개체 커버리지 | 섹션@1 | MRR |
| --- | --- | --- | --- |
| 단일 검색 | 60% | 0.88 | 0.938 |
| **개체 분할** | **100%** | **1.00** | **1.000** |

2번(재작성)이 없으면 커버리지는 100%가 되지만 **근거가 비대칭**해진다. 같은 혼합 벡터를 필터로만
나눠 쓰면 한쪽은 「6. 배당에 관한 사항」을 물어오는데 다른 쪽은 `(첨부)연결재무제표 > 주석`을
물어온다. 부분질의는 개체가 하나뿐이라 단일 질의와 같은 품질이 나오고, 3사 배당 비교에서
세 회사 모두 「6. 배당에 관한 사항」으로 정렬됐다.

대가는 인코딩 횟수다. 300ms → 개체 2곳 900ms / 3곳 1,200ms. 비교 질의당 약 2초면 충분하다.

`ask.py`는 회사가 2곳 이상 잡히면 **자동으로** 분할한다. `--no-split`으로 끄면 위 실패를 재현할 수 있다.
`--company`로 직접 필터를 걸면 분할하지 않는다.

> 여기서 하드필터가 처음으로 값을 한다. 단일 회사 질의에서는 순위를 전혀 바꾸지 않았지만(2번 항목),
> 비교 질의에서는 이게 해법 전체다.

### 5. 같은 보고서의 정정 재제출본 — 규칙은 좁게 잡아야 한다

카카오 연구개발비 비교에서 상위 3건이 전부 `[카카오] [기재정정]사업보고서 (2023.12)`였다.
접수번호는 셋 다 달랐다(20240321 / 20240328 / 20240418). 정정 재제출 3회분이다.

"같은 (회사, 문서제목)이면 최신 접수번호만 남기자"고 전량을 세니 **문서의 64.1%**가 걸렸다.
그대로 했으면 큰 사고였다.

- 삼성E&A 「단일판매ㆍ공급계약체결」 **87회** — 87건의 서로 다른 계약이다. 이벤트 공시는 제목이
  같아도 매번 다른 사건이라 이 규칙을 쓰면 안 된다.
- CJ제일제당 「사업보고서 (2023.12)」 3건 — **접수번호가 셋 다 같다.** 한 공시가 본문·첨부재무제표로
  쪼개져 doc_id만 갈린 것이다. 이것도 중복이 아니다.

규칙을 좁히면: **정기보고서(periodic)이고, 제목이 같고, 접수번호가 다를 때만** 옛것이 밀려난 것이다.
정기보고서는 제목에 기간이 들어 있어(사업보고서 (2023.12)) 제목이 같으면 같은 보고서다.
이 기준으로 **19개 조합 / 22개 문서 / 14,442청크 (전체의 2.35%)**다.

`--latest-only`로 켠다. 기본은 꺼져 있다 — 특정 시점의 옛 공시를 일부러 찾는 질의도 있기 때문이다.

또 한 공시 문서에서 뽑는 청크 수를 `--max-per-doc`(기본 1)으로 제한한다. 같은 섹션이 여러 청크로
쪼개져 상위를 도배하는 것을 막는다.

### 6. 남은 실패 4건 — 그리고 섹션 블록리스트가 답이 아닌 이유

| id | 질문 | 1위로 올라온 것 |
| --- | --- | --- |
| e04 | 삼성화재해상보험 지급여력비율 | `[기재정정]사업보고서 > 정 정 신 고 (보고) > 3. 정정사항` |
| g04 | 환율 변동 영향 | `(첨부)재 무 제 표 > 주석 > 현대자동차주식회사` |
| s02 | 카카오 최대주주 | `I. 회사의 개요 > 2. 회사의 연혁` |
| s03 | 현대자동차 사업의 내용 | `I. 회사의 개요 > 5. 정관에 관한 사항` |

앞의 둘이 구조적 보일러플레이트처럼 보여서 **섹션 블록리스트로 제외**하려 했다. 전량을 세어보니
후보가 30,004행(4.88%)이었고, 본문을 열어보니 **제외하면 안 되는 것들이었다.**

- `(첨부)재 무 제 표 > 주석 > <회사명>` **22,931행 (3.73%)** — 표지가 아니라 **진짜 주석 본문**이다.
  (첨부)재무제표 아래 Markdown 제목 계층이 주석 번호까지 안 내려가서 회사명이 마지막 마디로
  남은 것뿐이다. 안에는 일반사항·금융자산 분류·파생상품 회계처리가 다 들어 있다.
  지웠으면 실제 내용 4%를 날렸다.
- `정 정 신 고 (보고)` **5,894행 (0.96%)** — 섞여 있다. 61자짜리 순수 표지도 있지만,
  「정정 전 / 정정 후」 대비표와 재고자산 세부내역 같은 실제 수치 표도 들어 있다.

**결론: 깨끗하게 지울 노이즈 클래스는 없다.** (5번 항목에서 같은 실수를 또 할 뻔했다 —
필터를 만들기 전에 걸리는 건수를 세고 본문을 열어보는 것이 이 데이터에서는 매번 값을 했다.) 이건 삭제 문제가 아니라 **순위 낮추기** 문제다.
다만 「정정 전 / 정정 후」 대비표는 답변 생성 단계에서 위험하다 — 생성기가 이미 정정된
**옛날 값**을 사실인 것처럼 인용할 수 있다. 근거를 보여줄 때 문서 제목의 `[기재정정]` 표시를
반드시 함께 넘겨야 한다.

그리고 g04는 확인해 보니 **실패가 아니었다.** `(첨부)재 무 제 표 > 주석 > 현대자동차주식회사`
청크 안에 환율 5% 변동이 세전이익에 미치는 영향 표(USD 122,178 / EUR 45,957 백만원)가
그대로 들어 있다. 섹션 경로에 "환율"·"위험"이 안 적혀 있어 라벨이 못 잡았을 뿐이다.

> **지표가 실제보다 낮게 나온다.** `expect_any`는 섹션 경로와 문서 제목만 본다. (첨부)재무제표
> 아래 청크는 경로가 회사명에서 끝나 내용이 무엇이든 라벨에 안 걸린다. 실측 90%는 하한선이고,
> 본문까지 보면 더 높다. 설정 간 비교에는 그대로 써도 되지만 절대값으로 인용하지 말 것.

s02·s03은 성격이 다르다. 「회사의 연혁」·「정관에 관한 사항」은 의미적으로 이웃한 다른 섹션이라
필터로 풀 수 없다. 재랭커나 질의 재작성이 필요한 영역이다.

## 온도·전력 관리

이 머신은 4×RTX 4090(각 450W)이라 전부 돌리면 1.8kW를 넘겨 전원이 내려간다.
실제로 강제종료가 잦았던 시점은 GPU 4장을 동시에 쓰던 임베딩 본 실행 때다.

이 실험은 **GPU 한 장만** 쓴다. 전 실행에서 최고 **31°C / 62W**로 발열 위험이 없었다.
다시 다GPU 작업을 돌릴 때만 상한을 걸면 된다.

```bash
# 관리자 권한 PowerShell
python -m src.eval.gpu_guard --cap 300      # 4장 합계 1.8kW -> 1.2kW
python -m src.eval.gpu_guard --cap default  # 원복
```

`gpu_guard`가 하는 일:

- `select_gpu(n)` — torch import **전에** `CUDA_VISIBLE_DEVICES`를 고정한다. 이후 torch가 보는 장치는 `cuda:0` 하나뿐이다.
- `apply_memory_fraction` — GPU 3은 디스플레이 GPU라 80%, 나머지는 90%로 프로세스 메모리 상한을 건다.
- `cooldown` — 질의 전 온도를 재고 임계치(기본 80°C)를 넘었으면 70°C까지 내려올 때까지 막는다.
- `TempMonitor` — 실행 내내 2초마다 샘플링해 최고 온도·전력을 리포트에 남긴다.

`--gpu 3`을 주면 경고한다. 데스크톱 프로세스 20여 개가 붙어 있는 GPU라 메모리를 뺏으면
OOM이 아니라 무증상 정지로 나타난다.

### 알아둘 것 1: `expandable_segments`는 이 머신에서 무효다

임베딩 때 넣었던 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`가
**Windows + torch 2.7.1+cu118에서는 지원되지 않는다.** 실행하면 PyTorch가 경고한다.

```
UserWarning: expandable_segments not supported on this platform
```

설정해도 조용히 무시된다. GPU 3 메모리 경합 대책은 `--mem-fraction` 쪽만 실효가 있다.

### 알아둘 것 2: 콘솔 인코딩

Windows 기본 콘솔이 cp949라 한글·em dash 출력에서 `UnicodeEncodeError`로 프로세스가 죽는다
(임베딩 워커가 실제로 이걸로 죽었다: `logs/embed.0.log` 끝부분).
`src/eval/*`의 모든 진입점은 맨 위에서 `sys.stdout.reconfigure(encoding="utf-8")`를 건다.
새 스크립트를 추가할 때도 같이 넣을 것.

## 성능

| 항목 | 값 |
| --- | --- |
| 인덱스 로드 (dense 1.26GB fp16 -> GPU + sparse) | 약 10초 |
| bge-m3 모델 로드 | 20~65초 |
| 질의 인코딩 | 약 300ms |
| 전수 검색 (614,693건, 하이브리드) | 약 200ms |
| 비교 질의 (개체 2곳, 재작성 포함) | 약 2.1초 |
| 비교 질의 (개체 3곳) | 약 3.0초 |
| 48문항 전체 실행 | 약 80초 |

dense는 fp16으로 GPU에 통째로 올려 brute force로 훑는다. 61만 건 규모에서는 ANN 인덱스
(HNSW 등)를 만들 이유가 없다. 200ms면 충분하고 근사 오차도 없다.

## 다음 단계

검색은 확인됐다. 남은 것은 **가져온 근거로 답변을 만드는 단계**다. 백엔드는 아직 안 정했다.

- 로컬: `meta-llama/Llama-3.1-8B-Instruct`가 HF 캐시에 있다. 추가 비용 없이 GPU 1장으로 돈다.
- API: `openai` 2.15.0이 깔려 있으나 키가 설정돼 있지 않다.

`retrieval_eval.json`이 그대로 생성기 입력이 되도록 만들어 두었다.

생성기에 근거를 넘길 때 지킬 것:

- `document_title`과 `section_path`를 본문과 함께 넘긴다. 특히 `[기재정정]` 표시는 반드시 넘긴다 —
  「정정 전 / 정정 후」 대비표를 보고 이미 정정된 옛 값을 인용하는 사고를 막아야 한다.
- 비교 질의는 `search_multi()`의 결과를 쓴다. 회사별로 균등하게 실린 근거여야
  한쪽만 보고 비교를 지어내지 않는다.
- 근거에 답이 없으면 없다고 하도록 지시한다. 검색이 90% 맞아도 나머지 10%에서
  그럴듯한 오답을 만들면 전체를 못 믿게 된다.
