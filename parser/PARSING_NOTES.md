# DART 공시 파싱 — 예외사항 정리

`corpus/raw` 아래 4개 문서군(exchange, major, holding, periodic)을 마크다운으로
바꾸면서 실제로 마주친 예외 케이스와, 그걸 처리한 방식을 정리한다. 최종
파이프라인은 `rag_pipeline.py`가 지휘하고, 문서군별 실제 변환은 각 `*_parser.py`가
맡는다.

```
corpus/raw/{exchange,major,holding,periodic}/**  →  각 문서군 parser  →  마크다운
                                                            │
                                          rag_pipeline.py가 헤더(회사명/동의어) 부착
                                                            │
                                                   corpus/rag/*.md 저장
```

---

## 공통 예외사항 (4개 문서군 전부 해당)

문서군마다 원문 형식(HTML vs DSD-XML)이 다르지만, 아래 문제들은 네 파서 모두에서
똑같이 나타나 똑같은 방식으로 처리했다.

### 1. 인코딩 표시를 믿을 수 없음
원본은 전부 UTF-8인데, **exchange의 HTML만 `charset=euc-kr`이라고 잘못 적혀 있다.**
적힌 대로 읽으면 전부 깨진다. → 헤더 표시를 무시하고 바이트를 직접 UTF-8로 읽는다.

### 2. DSD-XML(major/holding/periodic)은 정식 XML이 아님
본문에 `<별표3-3>` 같은 꺾쇠, 이스케이프 안 된 `&`가 그대로 들어있다. 정식 XML
파서(`lxml` 등)를 쓰면 이런 문서가 조용히 깨지거나 사라진다.
→ 관대한 자체 HTML 파서(`html.parser` 기반)를 만들어 씀. `<` 다음이 영문자일 때만
태그로 인식하고, 한글/숫자/기호가 오면 그냥 글자로 남겨서 안 깨지게 한다.

### 3. `&이름` 뒤에 세미콜론을 함부로 붙이면 안 됨
`html.parser`는 `&` 뒤에 알파벳이 오면 특수문자 시작으로 오인한다. 그런데 원본에
세미콜론이 있었는지는 파서가 알려주지 않는다. 무조건 `&이름;`으로 복원하면
**없던 세미콜론을 만들어낸다** — 예: 원본 `삼성E&A` → `삼성E&A;`로 깨진 사례가
**exchange에서 73건** 발생. → 진짜 HTML 특수문자 이름(`amp`, `lt` 등)일 때만
세미콜론을 붙이고, 아니면 `&이름` 그대로 둔다. (major/holding/periodic에도 동일 로직 적용)

### 4. 값이 `-`인 항목은 기본으로 제거
공시 서식에는 안 쓰는 칸이 많아 그대로 두면 지저분해진다. 단
`해당사항없음`/`미해당`/`해당`/`아니오`는 **뜻이 있는 응답이라 항상 남긴다.**
(`--keep-empty` 옵션으로 원본 전체 보존 가능)

### 5. 나란한 라벨 칸 중복 제거는 "라벨 칸에만" 적용
같은 글자가 나란히 붙은 라벨 칸(rowspan/colspan으로 생긴 중복)은 하나로 합친다.
단 **값 칸까지 합치면 안 된다** — 정정 비교표의 `| 2. 계약내역 | - | - |` 같은
행이 3칸 → 2칸으로 줄어 표가 끊긴다. (실제로 이 실수 때문에 exchange 정정
비교표 631개 중 564개만 잡혔던 적이 있음 → 라벨 칸으로 한정해 631/631 복구)

### 6. "L L V…" 행에서 라벨이 2개 이상이면 앞쪽을 대분류로 승격
한 행에 라벨이 여러 개 연달아 나오고 그 다음 값이 오는 경우("L L V..."), 마지막
라벨 하나만 소분류로 보고 앞쪽 라벨들은 그 행 전체의 대분류로 승격시켜 뒤따르는
라벨-값 쌍에도 물려준다(row_ctx). ⚠️ 라벨 두 개가 대등한 열(예: "구분"/"항목")인
표에 이 규칙을 적용하면 없는 계층을 만들어낼 위험이 있음 — 지금까지 관찰된
데이터에서는 항상 대분류/소분류 관계였다.

### 7. rowspan은 항상 계층을 의미하지 않음
예: 고려아연 20250120800751 문서에서 `[6. 기타 투자판단…(rowspan=2 colspan=2)][내용]`
다음 줄에 `[※ 관련공시][-]`가 오는 경우, rowspan은 단지 칸 높이를 맞추려는
용도이지 "6. 기타 투자판단… > ※ 관련공시"라는 진짜 계층이 아니다. 그대로
물려받으면 잘못된 계층 구조가 생긴다 → 이런 표시 전용 rowspan은 물려받지 않도록 처리.

### 8. 회사명 동의어(alias)는 문서군 4개를 통틀어 통일
회사명이 담기는 자리가 문서군마다 다르다 — exchange는 HTML `<title>`(공시 당시
표시명, 약칭 위주), major/holding/periodic은 XML `<COMPANY-NAME>`(정식 등기
법인명). 문서 한 건만 보고 동의어를 만들면 "에이치엠엠 주식회사"로 검색 시
periodic·major·holding 문서는 걸리는데 exchange 문서는 하나도 안 걸리는 등
문서군마다 검색 결과가 달라지는 문제가 생긴다.
→ 저장 전에 `corpus/raw` 전체를 가볍게(표·문단 처리 없이 회사명 태그만) 훑어
회사(`corp_code`)별로 네 문서군에서 나온 모든 표기를 모으는
`CompanyAliasRegistry`를 만들고, 문서군에 상관없이 같은 회사면 같은 동의어
목록을 붙인다. 사명이 바뀐 회사는 공시 당시 옛 이름도 자동으로 동의어에 포함.
(`--no-unify-aliases`로 예전 방식 — 문서 자체의 옛 이름만 사용 — 로 되돌릴 수 있음.
단 이 통합 방식은 `raw_root`로 `corpus/raw` 전체를 넘겨야 효과가 있고, 문서군
폴더 하나만 넘기면 다른 문서군 표기를 모을 수 없다.)

### 9. periodic만: 한 접수번호에 원문이 여러 개
본보고서 + 감사보고서(`00760`) + 연결감사보고서(`00761`)까지 최대 3개 원문이
같은 접수번호 폴더 안에 있을 수 있다. 개별 파서는 파일 하나만 처리하고,
여러 파일을 하나의 접수번호로 묶는 것은 `rag_pipeline.py`의 파일명 규칙이
담당 — 파일명은 `{회사명}_{문서군}_{문서ID}.md`이되, 접수번호가 겹치면
첨부번호 꼬리(`_00760`)를 붙여 구분한다.

## exchange (거래소공시, HTML) — `exchange_parser.py`

**원본**: 한국거래소(KRX) 공시 HTML. **처리 건수**: 1,469/1,469 변환 성공.

### 처리한 예외
- **`<br>` 태그 속성명이 두 가지로 갈림**: `<br xmlns:java="...">`(1,467건)과
  `<br java="...">`(369건)가 섞여 있다. 속성명을 하나로 고정하면 369건이 샌다
  → 두 형태 모두 인식하도록 처리.
- **XML 선언 찌꺼기**: `<!--?javax.xml.transform.disable-output-escaping?-->`
  같은 처리 지시어 잔재를 제거.
- **`<a href="주소">글자</a>` → 마크다운 링크**: `[글자](주소)`로 변환.
- **`.noprint` 더미 span**: 1,469/1,469 문서 전부에 존재하는 화면 전용(인쇄 안 됨)
  더미 span을 본문 훑기 전에 선제거.
- **정정공시 판별은 제목 텍스트로**: `div[id^=LIB_]` 존재 여부로 정정 여부를
  판단하면 안 된다 — 이 상자를 정정 블록과 부록 블록이 같이 써서 660건이
  잡히고 그중 29건이 잘못 부풀려진다. 대신 **`정정신고(보고)` 제목** 문자열로
  판별 (확인 결과 631건 = 비교표 631건과 완전히 일치).
- **관련공시 링크 셀은 label 없이도 값으로 인정**: 셀 안에 `xforms_input`이
  없어도 링크(`<a>`)가 들어있으면 값으로 처리. 이 예외가 없으면 "관련공시"
  셀 748건에서 주소가 통째로 사라진다.
- **표 행 분류**: 비교표(머리글+데이터 행) / 섹션 제목(전체 폭 라벨 1칸) /
  자유 서술(전체 폭 값 1칸) 세 가지로 분류. 30,525행 전수 검증 결과
  미분류 0건.

### 최종 결과물
`{회사명}_exchange_{문서ID}.md` — 정정 비교표는 `| 항목 | 정정사유 | 정정전 | 정정후 |`
형태 표로, 일반 항목은 `- **N. 항목명**: 값` 목록으로 렌더링.

## major (주요사항보고서, DSD-XML) — `major_parser.py`

**원본**: DSD-XML(`<COMPANY-NAME>`, `TD/TE/TU/TH` 태그 체계). **처리 건수**: 598/598.

### 처리한 예외
- 공통 예외 1~8 전부 해당 (인코딩, 관대한 파서, `&` 세미콜론, `-` 제거, rowspan 등).
- **정정공시 판별**: `<CORRECTION>` 태그 유무로 판정. manifest의 `is_correction`과
  598/598 완전 일치 확인.
- **표 하나의 행만 모음**: 중첩 표(126개)의 행이 부모 표 처리에 섞이면 안 되므로
  분리해서 처리. 셀 안에 들어있던 중첩 표는 부모 표를 다 낸 뒤 이어서 낸다.
- **라벨/값 신호**: `TD`/`TH` = 라벨, `TE`/`TU` = 값. `TE`는 `ACODE`,
  `TU`는 `AUNITVALUE`를 항상 갖고 있어 DART 필드코드를 그대로 보존
  (`--json` 산출물의 "필드코드"). 단 `<THEAD>` 있는 표 안에서는 `TD`도
  라벨이 아니라 데이터로 취급 — **표 하나 단위로 먼저 판단**해야 함.
- **colspan 제거는 표 전체 기준**: `_live_columns()`가 "모든 버퍼 행에서 옆칸과
  완전히 같은 열"만 제거. 표지 레터헤드처럼 합쳐진 칸 위치가 행마다 다르면
  이 조건이 안 맞아 문제가 되는데, major에는 이런 표지 패턴이 없어 그대로 둠
  (holding/periodic에서는 다르게 처리 — 아래 참조).
- **`<COMPANY-NAME>` 등기명과 폴더명 불일치**: 139건에서 표기 차이(대부분
  법인격 표기 차이, 예: `네이버(주)`→`NAVER`), 그중 진짜 사명 변경이 9건
  (예: 대우조선해양→한화오션). 마크다운 본문에는 안 넣고 키-값 사전(JSON)에만 보존.

### 알려진 미해결 문제
- **문단 융합(공백 없는 결합) 버그** — holding/periodic에서 고친 4개 버그 중
  "제목 소실"·"감사표 값 소실"·"부터/까지 접미사 소실"에 해당하는 원문 패턴
  자체가 major에는 없어 문제가 안 되지만, **문단 융합 버그(굵은 소제목이
  다음 문장에 그대로 들러붙는 문제)는 major 598건 중 343건에서 실제로
  나타나고 아직 고치지 않았다.**

### 최종 결과물
`{회사명}_major_{문서ID}.md`. 표 47,452행 전수 분류 검증 — 미분류 0건.

## holding (대량보유상황보고서, DSD-XML) — `holding_parser.py`

**원본**: DSD-XML. **처리 건수**: 1,083/1,083.

major_parser.py와 같은 골격(관대한 HTML 파서, 셀 모델, 행 분류 알고리즘)을
쓰되, 원문을 전수 훑어 확인한 사실에 맞춰 두 가지를 더 처리했다.

### major와 다르게 처리한 것

1. **머리글 없는 표의 진짜 머리글 찾기**: `<THEAD>` 없이 배경 음영
   (`USERMARK` 안 `BC0X...` 코드)만으로 머리글을 표시하는 표가 있다(재무제표
   주석 표에 흔함). 이 신호는 `TD`에만 붙고 `TE`/`TU`에는 전혀 안 붙는다.
   놓치면 "구분1/구분2/…" 같은 가짜 머리글로 "당기말 유동" 같은 실제
   항목명이 사라진다. → `USERMARK`에 `BC0X` 패턴이 있는 `TD`를 머리글
   칸으로 인식. holding 전체에서 **1개** 표가 이 규칙으로 살아남.
   (단, 표 전체가 데이터 행 없이 통째로 배경 음영이면 머리글로 오판하지
   않고 그냥 문단/표로 흘려보냄.)
2. **colspan 제거를 행 단위로 판단**: major의 `_live_columns()`는 표 전체
   기준("모든 행에서 옆칸과 완전히 같은 열")이라, 표지 레터헤드처럼 합쳐진
   칸 위치가 행마다 다르면 조건이 안 맞아 글자가 중복 출력된다. →
   `_render_row()`는 표 전체가 아니라 **행 하나 안에서만** "바로 왼쪽 칸과
   같은 셀 객체인가"를 판단해서 지운다. 행마다 독립 판단하므로 colspan
   위치가 들쭉날쭉해도 항상 맞게 지워진다.

### 그 외 처리한 예외
- 공통 예외 1~9 전부 해당.
- **값이 먼저 오는 라벨-값 순서(U-L 역순)**: 보통 라벨(L) 다음 값(V) 순서인데,
  `U"2023년 12월 31일" L"현재기준"`처럼 값이 먼저 나오는 경우를 별도 처리.
- **표지 콜론 라벨** — `회 사 명 :`처럼 글자 사이가 벌어진 라벨을 정리해
  `회사명`으로 다듬으면서 공백·콜론을 제거하는 로직(`_colon_kv`). → 3차
  검증(아래)에서 "놓친 칸"으로 잡힌 6,349개가 전부 이 의도된 동작임을 확인.

### 본문 손실 검증에서 발견해 고친 버그 (holding·periodic 공통)
1. **재무제표 주석 제목 소실** — HMM 분기보고서 표본 1건에서 제목 136개 중
   83개(61%) 소실. 원인: `<TITLE>`이 `SECTION-N`/`COVER`/`CORRECTION` 바로
   밑에만 있다고 가정하고, 그 외(`TABLE-GROUP` 등)에 있으면 "이미 처리한 것"
   으로 오판해 건너뜀. → 부모가 이미 소비하지 않았으면 진짜 제목으로 인정.
2. **감사보고서 표의 마지막 값 소실** — periodic 전체 208,861건 규모. 원인:
   라벨-값을 번갈아 묶는 로직이, 행이 값으로 끝나고 그 값의 라벨이 같은 행에
   없으면(위쪽 행에 rowspan으로만 걸림) 마지막 값을 그냥 버림. → rowspan으로
   물려받은 대분류(ctx)만으로도 키를 만들도록 수정 (감사보고서 "감사업무
   수행내용" 표처럼 라벨이 훨씬 위쪽 행에 rowspan으로만 걸린 경우 대응).
3. **굵은 소제목이 다음 문장에 들러붙음** — `<SPAN>나. 소수주주권</SPAN>회사는...`
   처럼 원문에 공백이 없으면 "나. 소수주주권회사는"으로 붙어 오독됨. →
   태그 경계에서만 공백 삽입 (단, 모든 글자 조각 사이에 공백을 넣는 첫 시도는
   `html.parser`가 이스케이프 안 된 `&` 때문에 쪼갠 조각(`P&A인수하여` →
   `P`/`&A인수하여...`)에도 공백을 끼워 "P &A 인수하여"로 깨지는 2차 버그를
   유발 → 태그에서 나온 조각과 맞닿을 때만 공백을 넣도록 재수정).
4. **"부터"/"까지" 접미사 라벨 소실** — 거의 모든 periodic 사업연도 표에서
   발생. 원인: "L V L"로 행이 끝나면(예: 사업연도/값/부터) 앞의 L-V만 짝짓고
   남는 라벨(부터/까지)은 "짝지을 값이 없다"며 버림. 값 자체는 안 빠지고
   접미사만 빠져서, 문서 전체 3자 이상 토큰 집합 비교(65개 표본)로는 못 잡고
   **사용자가 직접 파일을 열어 발견**. → "L V L"로 끝나면 마지막 라벨을
   새 항목이 아니라 방금 짝지은 값의 접미사로 처리(단, 뒤에 "L V L V"처럼
   진짜 다음 쌍이 더 있으면 건드리지 않음).

### 검증 방법 (holding·periodic 대상, exchange·major는 미실시)
- **토큰 비교**: 원문 태그 제거 후 3자 이상 한글/영숫자 토큰 집합 vs 결과 md
  토큰 집합 대조 (65개 표본) → 최종 평균 손실 0.12%, 남은 손실은 전부 의도적
  제외(이미지 파일명, `<SUMMARY>` 메타데이터).
- **구조 직접 대조**: 칸에 글자가 있는데 결과 조각이 0개인 표(표 전체 소실)와,
  원문 `<TITLE>` 개수 대비 산출 제목 개수를 100개 표본에서 직접 셈 → 표 소실
  0건, 제목 15% 이상 비는 문서 0건.
- **표 단위 정밀 대조(3차)**: 문서 전체 토큰 집합 비교는 빠진 낱말이 문서
  다른 곳에 우연히 있으면 못 잡는 사각지대가 있다(실제로 버그 4번을 이
  방식으로는 못 잡고 사용자가 직접 찾음). → 범위를 표 하나로 좁혀, 표 각
  칸의 글자(토큰화 안 함, `--keep-empty`로 `-` 값도 포함)가 그 표 자신의
  출력 안에만 있는지 holding·periodic 2,549건 전체 대상으로 재검증 →
  놓친 칸 6,349개 발견 → 전수 분석 결과 100% `_colon_kv`의 의도된 동작
  (위 항목), 그 외 원인으로 놓친 칸 0건.

## periodic (사업/분기/반기보고서·감사보고서, DSD-XML/PDF) — `periodic_parser.py` (+ `pdf_periodic_parser.py`)

**원본**: DSD-XML(대다수) + PDF(예외 3건). **처리 건수**: 1,466/1,466
(`*_viewer.html` 3건은 제외 — 원본 XML 자체가 없음, PDF로만 존재해
`pdf_periodic_parser.py`가 별도 처리).

holding과 완전히 같은 골격(머리글 없는 표의 배경 음영 탐지, 행 단위 colspan
제거)을 공유한다.

### 처리한 예외
- 공통 예외 1~9 + holding의 두 가지 추가 처리(배경 음영 머리글, 행 단위 colspan) 전부 해당.
- **배경 음영 머리글 탐지 효과가 압도적으로 큼**: periodic은 재무제표 주석
  표가 매우 많아, 이 규칙이 실제 머리글을 살린 표가 **43,998개**에 달함
  (holding은 1개뿐 — 문서 성격 차이).
- **holding과 동일한 4개 버그 수정 전부 해당** (제목 소실·감사표 값
  소실·문단 융합·부터/까지 소실) — periodic이 버그 2·4의 발생 규모가
  가장 컸던 문서군(각각 208,861건, 거의 전체 문서).
- **PDF 원문 3건**: 원본 XML이 없고 `_viewer.html`만 있는 문서는
  `pdf_periodic_parser.py`가 별도 처리 — 표 셀의 라벨/값 추정, 표지 문단의
  키-값 변환, 페이지 단위 블록을 chunk 목록으로 변환하는 로직이 XML
  기반 파서와 별개로 존재.
- **`<COMPANY-NAME>`**: periodic에서는 "보고 대상 회사(자기 자신)"의 등기명 —
  major/holding처럼 상대방(발행회사 등)이 아니라 본인 회사명이라는 점이 다름.

### 최종 결과물
`{회사명}_periodic_{문서ID}.md`, 첨부(감사보고서 등)가 있으면
`{회사명}_periodic_{문서ID}_{첨부번호}.md`. 표 1,538,775행 전수 분류
검증 — 미분류 0건 (4개 문서군 중 표 규모가 압도적으로 크며, 재무제표
주석·감사보고서가 다수 포함되어 위 버그 발견 대부분이 이 문서군에서 나옴).
